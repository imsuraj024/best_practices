# Contributing

Thank you for contributing to the Flutter Engineering Playbook.

## What belongs here

Contributions should improve practical Flutter engineering guidance, examples, templates, or checklists.

Good contributions:

- Clear, production-oriented guidance
- Runnable Flutter/Dart examples
- Anti-pattern vs recommended-pattern comparisons
- Performance, security, testing, or architecture improvements
- Documentation fixes backed by current Flutter/Dart behavior

## Documentation standard

Each practice should explain:

1. Overview
2. Problem
3. Recommended approach
4. Implementation
5. Why it works
6. Trade-offs
7. Common mistakes
8. Testing approach
9. Performance or security implications where relevant
10. When not to use it

## Pull requests

- Keep changes focused.
- Use clear filenames and headings.
- Keep examples runnable where practical.
- Do not include secrets, credentials, or production customer data.
- Update related checklists or navigation when adding a new practice.

## Quality checks

Before opening a pull request, run the relevant Flutter/Dart formatting, analysis, and tests for changed examples.

For documentation-only changes, verify that links and referenced paths exist.
